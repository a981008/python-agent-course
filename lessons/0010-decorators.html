一、心智模型：装饰器 ≈ 代理与拦截器（4 分钟）

Java 的注解（@Override/@Transactional）只是贴在代码上的元数据，要靠反射或 AOP 才生效。Python 装饰器直接就是函数：接收一个函数、返回一个包装过的新函数，定义即执行。对照：

对照 — Java → Python
Spring @Transactional（AOP 拦截）    →  @log / @retry（装饰器本身就是拦截器）
动态代理 InvocationHandler          →  包装函数 wrapper（收原函数、返回新函数）
Servlet Filter 链                   →  装饰器叠放 @a @b f（自下而上包裹）
注解要反射/AOP 才生效               →  装饰器是普通函数调用，一行魔法都没有
函数回调（FunctionalInterface 参数）→  函数是一等公民，直接当参数传

底层只需要一个事实：Python 里函数是值——可以赋给变量、塞进 dict、当参数传。装饰器只是把"包一层再还回去"写成了惯用形式。

二、三段式解剖：@log（5 分钟）

PYTHON — 装饰器三段式
def log(fn):                     # ① 收函数
    def wrapper(*args, **kwargs):    # ② 包一层（万能透传签名）
        print(f"调用 {fn.__name__} 参数 {args}")
        return fn(*args, **kwargs)   # ③ 透传调用、原样返回结果
    return wrapper

@log
def add(a, b):
    return a + b

# @log 这行 ≈ add = log(add)   ← 语法糖，一行不差
# add(1, 2) → 先打印，再返回 3
# *args/**kwargs 是第 3 课的积木：不管原函数什么签名都能接住并原样传下去

三、带参装饰器 = 装饰器工厂（三层）（6 分钟）

@log 直接贴函数名；@retry(times=3) 带了参数——多了一层。规则：带参装饰器是"造装饰器的工厂"，三层各管一件事：

PYTHON — @retry(times=3)：工厂三层
def retry(times):                # 第 1 层：收参数 → 返回真装饰器
    def deco(fn):                # 第 2 层：收函数 → 返回包装（同三段式）
        def wrapper(*args, **kwargs):   # 第 3 层：干活的包装
            last = None
            for _ in range(times):
                try:
                    return fn(*args, **kwargs)
                except Exception as e:
                    last = e     # 失败记住，再试
            raise last           # 全失败：把最后一次异常抛出去
        return wrapper
    return deco

@retry(times=3)
def call_llm(prompt): ...

# 为什么三层？@retry(times=3) 先执行 retry(3) 得到 deco，再 deco(call_llm) 得到包装
# 无参装饰器两层，带参三层——数 @ 的"层数"就能读懂任何装饰器

四、functools.wraps 与 @tool 注册表（4 分钟）

PYTHON — wraps 保身份；注册表收工具
import functools

def log(fn):
    @functools.wraps(fn)         # 把 fn 的 __name__/__doc__ 拷给 wrapper
    def wrapper(*args, **kwargs):
        return fn(*args, **kwargs)
    return wrapper
# 不加 wraps：add.__name__ 变成 "wrapper"——调试器、日志、文档全瞎

TOOLS = {}                       # Agent 工具注册表（function calling 的原型）

def tool(fn):
    TOOLS[fn.__name__] = fn      # 按 name 收进注册表
    return fn                    # 原样返回——注册不改变行为

@tool
def get_weather(city):
    return f"{city}: 晴"

# get_weather 仍可正常调用；TOOLS 里多了一个可被 Agent 检索的工具
# 加新工具 = 写新函数 + @tool，主循环零改动——开闭原则

这就是所有 Agent 框架注册工具的方式（LangChain 的 @tool、OpenAI function calling 的工具清单）。第 13 课综合实战会直接用它。

参考实现（先自己写完再看）

import functools

# 任务 1 — @log：三段式 + wraps
def log_calls(fn):
    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        LOGBOOK.append((fn.__name__, args))
        return fn(*args, **kwargs)
    return wrapper

# 任务 2 — 带参装饰器 = 工厂三层
def retry(times):
    def deco(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            last = None
            for _ in range(times):
                try:
                    return fn(*args, **kwargs)
                except Exception as e:
                    last = e
            raise last
        return wrapper
    return deco

# 任务 3 — @tool 注册表（注册不改行为）
def tool(fn):
    TOOLS[fn.__name__] = fn
    return fn


自评清单：① wrapper 是 *args, **kwargs 万能签名吗？记录发生在调用前还是后？② retry 工厂是不是三层？全失败抛的是"最后一次"的异常吗？③ tool 返回的是 fn 本身还是 wrapper——为什么注册器不该改变行为？





六、检索练习：先答后看（关补全）




  
Q1 · @deco 紧跟 def f(): ...，等价于哪一句？

  
  
  
  
装饰器就是语法糖：@deco def f ≡ f = deco(f)。和 Java 注解的本质区别在这——Python 装饰器是立即执行的普通函数调用，不需要反射或 AOP 框架。






  
Q2 · 为什么 @retry(times=3) 要写成三层函数？

  
  
  
  
@retry(times=3) 先执行 retry(3) 得到 deco，再 deco(fn) 得到 wrapper。无参装饰器两层、带参三层——数层数就能读懂任何装饰器。






  
Q3 · functools.wraps(fn) 解决什么问题？

  
  
  
  
不加 wraps，fn.__name__ 会变成 "wrapper"——调试器、日志、文档工具全瞎。注册器/框架要靠 __name__ 找函数（比如 @tool 按 name 注册），所以工程装饰器一律带 wraps。
