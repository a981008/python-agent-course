第 11 课 · 并发模型与 GIL：线程、进程与协程怎么选

Mission: Python（Agent 开发与面试算法） · 预计 30 分钟 · 关掉 AI 补全再开始

本课的 win：面试高频题"Python 多线程有用吗"能一句话答到点上——IO 密集有用，CPU 密集靠多进程。验收：讲清 GIL 的边界，并能按瓶颈选出线程池 / 进程池 / 协程。

一、三种并发模型：先看瓶颈，再看工具（3 分钟）

对照 — Java 并发 → Python 并发Thread / Runnable              →  threading.Thread
ExecutorService + Future       →  concurrent.futures.Executor
synchronized / ReentrantLock   →  threading.Lock（with 语法）
BlockingQueue                  →  queue.Queue
CompletableFuture 组合         →  asyncio（下一课，单线程事件循环）
ForkJoinPool / 多进程            →  multiprocessing / ProcessPoolExecutor

并发不是"越多线程越快"，而是让等待重叠。先判断任务瓶颈：

  • IO 密集：等网络、磁盘、数据库。等待时 CPU 空闲，适合线程或协程。
  • CPU 密集：纯计算、编解码、图像处理。需要真并行，CPython 下用多进程。

二、GIL：同一时刻只有一把"解释器锁"（4 分钟）

PYTHON — 一个反直觉的实验import threading, time

def burn(n):
    x = 0
    for i in range(n):
        x += i * i
    return x

N = 3_000_000
t0 = time.perf_counter(); burn(N); burn(N); print("串行", time.perf_counter() - t0)

t0 = time.perf_counter()
a = threading.Thread(target=burn, args=(N,))
b = threading.Thread(target=burn, args=(N,))
a.start(); b.start(); a.join(); b.join()
print("双线程", time.perf_counter() - t0)   # 通常并不更快

CPython 的 GIL（Global Interpreter Lock）保证同一进程内同一时刻只有一个线程执行 Python 字节码。所以纯计算开线程不会变快，只多了切换成本。

PYTHON — 但有三种情况 GIL 会让路# ① 阻塞式 IO（socket / 文件 / sleep）会释放 GIL，别的线程可以跑
# ② C 扩展可以在长计算里主动释放 GIL（numpy、hashlib 等）
# ③ 每执行一小段字节码会做一次线程切换检查（不是严格实时）

# 结论：
#   线程适合"等待多"的任务；CPU 并行要靠多进程。
#   Python 3.13+ 提供实验性的 free-threaded 构建（PEP 703），
#   但默认构建与课程环境仍按 GIL 模型理解。
面试追问"那为什么还有多线程程序跑得快"——因为大多数后端服务是 IO 密集：等数据库、等 RPC、等磁盘。GIL 在等待期间是释放的。

三、threading：线程、锁与队列（5 分钟）

PYTHON — 起线程与等待import threading

def work(name, n):
    print(f"{name} 开始")
    total = sum(range(n))
    print(f"{name} 完成 {total}")

t = threading.Thread(target=work, args=("A", 1000), daemon=True)
t.start()      # 启动
t.join()       # 等待结束（对应 Java 的 Thread.join）

# daemon=True：主线程退出时不等它（类似守护线程）
PYTHON — 竞态与 Lockcounter = 0
lock = threading.Lock()

def bump():
    global counter
    for _ in range(100_000):
        with lock:              # 等价于 lock.acquire() / try / finally: release()
            counter += 1

ts = [threading.Thread(target=bump) for _ in range(4)]
for t in ts: t.start()
for t in ts: t.join()
print(counter)                  # 没有 Lock 时通常小于 400000
PYTHON — 生产者 / 消费者：queue.Queue 自带线程安全import queue, threading

q = queue.Queue(maxsize=10)

def producer():
    for i in range(5):
        q.put(i)                # 队列满时阻塞
    q.put(None)                 # 结束信号

def consumer():
    while True:
        item = q.get()          # 队列空时阻塞
        if item is None:
            break
        print("处理", item)

threading.Thread(target=producer).start()
threading.Thread(target=consumer).start()

queue.Queue 内部已经加锁，是线程间传递数据最省心的方式；比共享变量 + 手动锁更不容易出错，对应 Java 的 BlockingQueue。

四、Executor：用线程池 / 进程池统一接口（4 分钟）

PYTHON — ThreadPoolExecutorfrom concurrent.futures import ThreadPoolExecutor, as_completed

def fetch(url):
    ...                          # 模拟 HTTP 请求

urls = ["https://a", "https://b", "https://c"]

with ThreadPoolExecutor(max_workers=8) as pool:
    futures = [pool.submit(fetch, u) for u in urls]
    for f in as_completed(futures):     # 谁先完成先处理
        print(f.result())

# 或者保持输入顺序：
# list(pool.map(fetch, urls))
PYTHON — ProcessPoolExecutor：绕过 GILfrom concurrent.futures import ProcessPoolExecutor

def cpu_heavy(n):
    return sum(i * i for i in range(n))

if __name__ == "__main__":       # Windows / spawn 启动方式必须守入口
    with ProcessPoolExecutor(max_workers=4) as pool:
        print(list(pool.map(cpu_heavy, [10**6] * 4)))

两个 Executor 接口完全相同，submit 返回 Future，result() 取结果、as_completed 按完成顺序消费。差异在底层：进程池的每个任务参数和返回值都要能 pickle，且子进程有独立内存。

PYTHON — 最佳实践：分批而不是一个任务一个 Futuredef chunks(seq, size):
    for i in range(0, len(seq), size):
        yield seq[i:i + size]

# 任务粒度太细 → 调度/序列化开销盖过收益
# 把 10 万条数据切成 1 万条一批，再交给进程池

五、选型决策：一张表记牢（3 分钟）

对照 — 场景 → 方案IO 密集 + 并发不高（几十）      →  ThreadPoolExecutor
IO 密集 + 并发很高（上千）      →  asyncio（下一课）
CPU 密集                        →  ProcessPoolExecutor / multiprocessing
需要进程间共享大量状态          →  多线程 + Lock，或改用外部存储
任务极短且数量巨大              →  批处理 + 协程/进程池，避免逐条调度

三条经验：

  • 先测再选：把串行基线跑出来，再比较线程池/进程池耗时（第 9 课的 timeit 能帮上忙）。
  • 能不用锁就不用：优先消息传递（Queue、Future 返回值），共享可变状态越少越好。
  • 进程池要守 if __name__ == "__main__":，否则 spawn 模式下会递归创建进程。

参考实现（先自己写完再看）

def chunk_ranges(n, workers):
    if workers <= 0:
        raise ValueError("workers 必须为正数")
    if n <= 0:
        return []
    workers = min(workers, n)
    base, rem = divmod(n, workers)
    out, start = [], 0
    for i in range(workers):
        size = base + (1 if i < rem else 0)
        out.append((start, start + size))
        start += size
    return out

def merge_counts(parts):
    total = {}
    for d in parts:
        for k, v in d.items():
            total[k] = total.get(k, 0) + v
    return total

def pick_pool(io_bound, cpu_bound):
    if io_bound and cpu_bound:
        return "hybrid"
    if cpu_bound:
        return "process"
    return "thread"


自评清单：① 切分是否不重不漏（最后一段结束等于 n）？② workers 超过 n 时是否退化为 n 段？③ merge_counts 是否处理了空列表？





七、检索练习：先答后看（关补全）




  
Q1 · CPython 默认构建里，4 个线程同时跑纯 CPU 计算，总速度通常？

  
  
  
  
GIL 保证同一时刻只有一个线程执行 Python 字节码，CPU 密集任务无法并行，线程切换还有开销。要真并行只能多进程（或实验性的 free-threaded 构建）。






  
Q2 · 批量调用外部 HTTP 接口（IO 密集），最轻量的并发方案是？

  
  
  
  
IO 等待时线程会释放 GIL，线程池足以重叠等待时间；进程池要多付进程创建与序列化成本，通常没有必要。asyncio 在更高并发下更省内存。






  
Q3 · 多线程同时对同一个计数器做  += 1，可能丢更新，正确做法是？

  
  
  
  
x += 1 不是原子操作（读、加、写三步），线程可能在中间切换。Lock 保证临界区互斥；也可用 queue.Queue 把结果交给单线程汇总。






  
Q4 · ProcessPoolExecutor 相比 ThreadPoolExecutor 的关键差异是？

  
  
  
  
多进程绕过 GIL 实现 CPU 并行，代价是进程启动、参数和返回值的 pickle 序列化，以及进程间不共享内存。数据量大时传输成本可能吃掉收益。
