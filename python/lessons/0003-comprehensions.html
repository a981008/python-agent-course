一、心智模型：推导式不是语法糖，是一种"声明式"习惯（3 分钟）

第 1 课你已经见过 [x for x in lst if cond]。这节课要把它练到不过脑子。先修正一个 Java 直译过来的误区：推导式读作"对每个元素产出什么"，而不是"如何循环"。

JAVA — Stream 链List<String> ids = orders.stream()
    .filter(o -> o.getAmount() > 100)
    .map(Order::getOrderId)
    .sorted()
    .collect(Collectors.toList());
PYTHON — 一行推导ids = sorted(o.order_id for o in orders if o.amount > 100)

注意结构：[表达式 for 变量 in 可迭代 if 条件]。if 在后面是过滤（对应 filter），if 在前面是转换（[x if cond else y for x in lst]，对应 map 里的三元判断）——这两者面试手写时最容易混，检索练习会专门考。

二、四种推导式 + 生成器表达式：完整展开

形式语法Java 对应典型用途
列表推导[f(x) for x in lst if cond]stream filter+map构建新列表（最常用）
字典推导{k: v for x in pairs}Collectors.toMap构建映射、键值对调
集合推导{f(x) for x in lst}Collectors.toSet去重收集
生成器表达式(f(x) for x in lst)lazy Stream直接喂给 sum/max/any

三个高频细节：

1. 嵌套循环按书写顺序展平。[x for row in matrix for x in row] 等价于两层 for 先外后内——读的时候从左往右就是循环顺序，和 Java 嵌套 for 的直觉一致。

2. 生成器表达式省一次中间列表。sum(x*x for x in nums) 比 sum([x*x for x in nums]) 少建一个临时列表——数据量大时是内存问题，不只是风格问题。给聚合函数传值时省略括号是惯用法。

3. 有变量名需求的循环别硬套推导。推导式适合"一条表达式能说清"的场景；出现两步以上逻辑（先算再筛再带中间量）时，老老实实写 for 循环——可读性优先于炫技，面试官看到三层嵌套推导反而扣分。

三、检索练习：先答后看（关补全）

凭记忆回答——答错的选项里的说法，就是你需要重点分辨的概念。

Q1 · [x*2 if x > 0 else 0 for x in nums] 中间的 if...else 起什么作用？

带 else 的三元表达式在 for 前面，是"转换"：每个元素都有产出。只有 for 后面不带 else 的 if 才是过滤（丢弃元素）。两者可以同时出现。

Q2 · sum(x * x for x in nums) 与 sum([x * x for x in nums]) 的核心区别？

生成器表达式惰性产出，逐个喂给 sum；列表推导先构建完整列表再聚合。结果相同，内存占用不同。

Q3 · 对列表去重且保持原顺序，惯用写法是？

set 无序，转回 list 后顺序不保证；dict 自 3.7 起保持插入序，dict.fromkeys 去重保序。sorted 是按大小排序，不是保原顺序。

参考实现（先自己写完再看）

def amount_map(orders: list[Order]) -> dict[str, float]:
    return {o.order_id: o.amount for o in orders if o.amount > 100}

def unique_tags(orders: list[Order]) -> list[str]:
    return list(dict.fromkeys(tag for o in orders for tag in o.tags))

def total_amount(orders: list[Order]) -> float:
    return sum(o.amount for o in orders)


自评清单：① amount_map 的 if 是不是在 for 后面（过滤位）？② unique_tags 两个 for 的顺序——先订单后 tag，从左往右读就是循环顺序？③ 三个函数里都没出现显式的 append / 中间变量？
