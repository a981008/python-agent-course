本课的 win：给一个支付函数搭出三层防御——自定义业务异常、失败重试、上下文管理器兜底。这套结构在 Agent 调用链（模型超时重试、工具异常兜底）里每天都会用到。另补两块高频盲区：金额必须用 Decimal，批量失败用 ExceptionGroup。

一、心智模型：checked 异常没了（4 分钟）

Java 把异常分 checked/unchecked，方法签名还要 throws 声明。Python 只有运行时异常：没有 throws 声明、没有编译器逼你接——异常也是对象，全部继承自 BaseException，业务异常统一继承 Exception。先对齐语法：

catch (IOException e)except OSError as e:as e 拿到异常对象
throw new XxxError("...")raise XxxError("...")throw → raise
throws IOException无想声明就写进 docstring
class XxxError extends Exceptionclass XxxError(Exception)自定义异常同款手法
try-with-resourceswith资源管理，第四节细讲

另一个思路差异：Java 习惯先检查再动手（LBYL，look before you leap），Python 习惯先动手再接异常（EAFP，easier to ask forgiveness than permission）——面试爱问这个：

LBYL — Java 习惯：先问再动if "user" in session:
    name = session["user"]
else:
    name = "游客"EAFP — Python 习惯：先动再接try:
    name = session["user"]
except KeyError:
    name = "游客"

取单个键用 session.get("user", "游客") 更简单；但逻辑一复杂（取值还要处理），EAFP 就赢了——不用把检查条件抄两遍。

二、try/except/else/finally 完整结构（6 分钟）

PYTHON — 四个块各管一件事try:
    result = call_model(prompt)          # 冒险的代码
except TimeoutError as e:                # 精确捕获，可写多个 except
    result = fallback
except (KeyError, TypeError):            # 元组 = 一口气捕获多种
    result = None
else:                                    # 无异常时才执行（成功路径）
    log.info("成功")
finally:                                 # 无论如何都执行（清理）
    release(resource)

三条纪律，都是 Java 带过来的好习惯，Python 里更严格：

① 精确捕获，别裸 except:——它会连 KeyboardInterrupt、SystemExit 一起吞（它们直接继承 BaseException，不走 Exception）；兜底用 except Exception as e。

② except 里别吞异常不留痕——至少记日志；需要向上传播时 raise（裸 raise 保留原 traceback）。

③ finally 放清理——或者直接用第四节的 with，让语言替你写 finally。

常见内建异常类型（面试手写代码会碰到）：

Python何时抛Java 近亲
ValueError类型对但值不对IllegalArgumentException
TypeError类型不对ClassCastException 近似
KeyError / IndexError键/下标越界IndexOutOfBoundsException
FileNotFoundError文件不存在FileNotFoundException

三、raise 与 raise ... from ...：异常链（6 分钟）

完整异常语法与内建类型：
参考 · 全语法速查表 · 异常处理 
PYTHON — 包装底层异常，保留原因try:
    resp = http_post(url, payload)
except ConnectionError as e:
    raise ModelCallError("模型调用失败") from e   # 异常链：__cause__ = e

from e 对应 Java 的 initCause：traceback 会把两个异常都打出来（"The above exception was the direct cause of..."），底层网络错误的信息一点不丢。Agent 项目里，工具层错误包装成业务错误时必须这样做——否则排查问题等于盲人摸象。

自定义异常要成体系：先建一个业务异常基类，具体异常继承它。这样上层捕获基类就能兜住一整族，和 Java 完全同款：

PYTHON — 异常层次class AgentError(Exception):
    """本项目业务异常基类"""

class ModelCallError(AgentError): ...
class ToolExecError(AgentError): ...

try:
    run_agent()
except AgentError:          # 一网打尽本项目的业务异常
    alert_oncall()

四、金额与精度：float 是近似，Decimal 是精确（5 分钟）

PYTHON — 0.1 + 0.2 为什么不等于 0.30.1 + 0.2                # 0.30000000000000004
0.1 + 0.2 == 0.3         # False

# 原因：0.1 在二进制里是无限循环小数，只能用近似值表示。
# 这不是 Python 的 bug —— Java 的 double、C 的 float 都一样（IEEE 754）。
PYTHON — 金额的正确答案：Decimal，且用字符串构造from decimal import Decimal, ROUND_HALF_UP

Decimal("0.1") + Decimal("0.2")         # Decimal('0.3') —— 精确十进制
Decimal(0.1)                            # ✗ 错：把已经近似的 float 带进精确类型

# 量化到"分"：
Decimal("19.99").quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)

# 纪律：金额一律 Decimal，且用字符串或整数构造。
def money_total(prices):
    total = sum(prices, Decimal("0"))
    return total.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)
JAVA 对照 — 同一套 BigDecimal 纪律new BigDecimal("0.1")     →  Decimal("0.1")      精确
new BigDecimal(0.1)       →  Decimal(0.1)        把 double 误差带进来
setScale(2, RoundingMode.HALF_UP)  →  quantize(..., rounding=ROUND_HALF_UP)
equals vs compareTo       →  Decimal 的 == 同时比较数值与指数，慎用
面试追问"那算钱怎么办"：答案就是 Decimal + 字符串构造 + 明确舍入模式。float 只用于科学计算和近似统计。

五、批量异常：ExceptionGroup 与 except*（4 分钟）

PYTHON — 3.11+：一次抛出一组失败try:
    raise ExceptionGroup("批量失败", [ValueError("a"), KeyError("b")])
except* ValueError as eg:
    print("值错误:", eg.exceptions)       # (ValueError('a'),)
except* KeyError as eg:
    print("键错误:", eg.exceptions)       # (KeyError('b'),)

# except* 不是 except 的别名：
#   每个分支独立处理同一组里的一类异常，未匹配的留给后面的 except*
#   和 asyncio.gather(return_exceptions=True) / TaskGroup 是天然搭档
PYTHON — add_note：给异常补充上下文（仍保持原类型）try:
    1 / 0
except ZeroDivisionError as e:
    e.add_note("分母来自配置文件 config.yaml")
    raise                                 # 裸 raise，保留原 traceback

# e.__notes__ == ['分母来自配置文件 config.yaml']
# 注意：是 raise，不是 raise e —— 后者会把栈从这里重置

设计取舍：普通业务错误继续用"一个异常 + raise ... from ... 链"；只有并发/批量任务同时失败时才需要 ExceptionGroup，否则调用方要多写一层 except*，得不偿失。

六、with 与上下文管理器：让语言替你写 finally（6 分钟）

Java 的 try-with-resources 需要 AutoCloseable；Python 的 with 需要上下文管理器——实现 __enter__/__exit__ 两个方法的对象。日常很少手写类，用 @contextmanager 把一个函数变成 CM：

PYTHON — yield 一分为二from contextlib import contextmanager

@contextmanager
def tagged(name):
    print("进入", name)        # yield 之前 = __enter__（with 进入时执行）
    try:
        yield name              # yield 的值 = as 后面的变量
    finally:
        print("退出", name)     # yield 之后 = __exit__（离开时必执行）

with tagged("数据库事务") as t:
    do_something()              # 即使这里抛异常，"退出"也会打印

结构记法：yield 前是入口、yield 后是出口、yield 的值就是 as。清理逻辑放 finally（或 yield 后面）——等会动手要写的"兜底层"正是这个套路：包住一段危险代码，指定的异常就地消化。

标准库里现成的 CM 优先用：open() 文件、contextlib.suppress(...)（等会动手就会手写一个；日常直接用它，别重复造轮子）、contextlib.closing()。

写完并通过全部测试后，展开对照参考实现自评：




参考实现（先自己写完再看）

# 任务 1 — 业务异常层
class InsufficientBalanceError(Exception):
    pass

def withdraw(balance: float, amount: float) -> float:
    if amount > balance:
        raise InsufficientBalanceError(f"余额不足: {balance} < {amount}")
    return balance - amount

# 任务 2 — 重试层
def retry_call(fn, times: int = 3):
    last = None
    for _ in range(times):
        try:
            return fn()
        except ValueError as e:
            last = e
    raise last

# 任务 3 — 兜底层（上下文管理器）
from contextlib import contextmanager

@contextmanager
def suppress_error(exc_type):
    try:
        yield
    except exc_type:
        pass



自评清单：① raise 出的异常带着"余额不足"消息吗？② 重试循环里是"用尽才抛最后一次异常"，不是"第一次失败就抛"？③ 非 ValueError 的异常没有重试（精确捕获的意义）？④ yield 写在了 try 里、except 只吞指定类型？





八、检索练习：先答后看（关补全）




  
Q1 · 为什么不能写裸 except:？

  
  
  
  
裸 except 捕获 BaseException 全家，包括 Ctrl+C（KeyboardInterrupt）和退出（SystemExit）——程序连"关不掉"。兜底请写 except Exception as e，它只接业务异常。






  
Q2 · raise NewError("包装") from e 里的 from e 是干什么的？

  
  
  
  
对应 Java 的异常 cause / initCause。traceback 会同时显示两个异常（"The above exception was the direct cause..."），Agent 调用链里把底层网络错误包装成业务错误时必用。






  
Q3 · @contextmanager 装饰的函数里，yield 的值去了哪里？

  
  
  
  
yield 前面的代码相当于 __enter__，后面相当于 __exit__；yield 的值就是 as 后面拿到的值。清理逻辑写在 yield 之后的 finally 里——即使 with 内部抛异常也会执行。






  
Q4 · Decimal("0.1") 与 Decimal(0.1) 的区别是？

  
  
  
  
Decimal 从字符串构造时能精确读入十进制位数；从 float 构造则会把二进制近似的真实值（0.1000000000000000055…）原样记下来。算钱永远用字符串或整数构造。






  
Q5 · except* 与 except 的关键区别是？

  
  
  
  
except* 是 3.11 为 ExceptionGroup 引入的：同一组里不同类型可以各自命中一个分支，未匹配的继续留给后面的 except*。
